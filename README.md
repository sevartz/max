## 1. Назначение проекта

Бот-администратор канала в мессенджере MAX, который зарабатывает каналу на рекламе,
**подходящей к каждому конкретному посту**.

Когда в канале выходит пост, бот понимает его тему, подбирает из каталога подходящее объявление
и присылает админу предложение с объяснением «почему» и ожидаемым доходом. Без одобрения админа
ничего не публикуется. После одобрения бот публикует рекламный пост с маркировкой и считает
просмотры, клики и деньги.

Для рекламодателей есть кабинет в боте (`/cabinet`) и мини-приложение MAX: создание объявлений,
бюджет, статистика.

## 2. Основной пользовательский сценарий

**Админ канала:**

1. Пишет боту `/start` и принимает условия (оферта 70% каналу / 30% платформе, согласие на
   обработку данных).
2. Добавляет бота администратором канала с правами «Читать все сообщения» и «Публиковать
   сообщения». Бот проверяет права и строит профиль канала по последним постам.
3. Публикует в канале пост.
4. Получает в личку предложение: объявление, «почему подходит», модель оплаты, ожидаемый доход,
   кнопки **✅ Одобрить / ❌ Отклонить / 🔄 Другой вариант / 🚫 Не предлагать категорию**.
5. Одобряет — через 1 минуту реклама выходит в канал с маркировкой `#Реклама` и кнопкой
   «Подробнее».
6. Смотрит доход в `/stats`, настраивает категории в `/settings`.

**Рекламодатель:** `/cabinet` → название компании → «Новое объявление» (заголовок, текст, ссылка,
категория, модель CPM/CPC/CPA, цена, бюджет) → «Запустить». Объявление сразу участвует в подборе.
В карточке — правка, пауза, демо-пополнение бюджета, статистика.

**Подписчик канала** видит рекламный пост и переходит по «Подробнее».

Подробно, с экранами и текстами бота, — [frontend-ux.md](backend/docs/frontend-ux.md).

## 3. Архитектура

```
             MAX Bot API (platform-api2.max.ru)
                 │ события: webhook (прод) или long polling (локально)
                 ▼
┌──────────────────────────── контейнер app (FastAPI, :8000) ────────────────────────────┐
│ /webhook/max ─► ingest (дедупликация) ─► таблица jobs ─► воркер ─► Dispatcher ─► хендлеры│
│                                                                    │                   │
│   подбор: анализ поста LLM (NVIDIA NIM) ─► эмбеддинг e5 ─► поиск pgvector ─► фильтры ─► │
│           оценка ─► объяснение LLM ─► предложение админу ─► публикация ─► учёт денег     │
│                                                                                        │
│ /miniapp/ (статика frontend)   /api/miniapp/* (API мини-приложения, подпись MAX)        │
│ /r/{token} (трекер кликов)     /postback (конверсии CPA)     /showcase (витрина)        │
└────────────────────────────────────────────┬───────────────────────────────────────────┘
                                             ▼
                          PostgreSQL 16 + pgvector (контейнер db)
```

- **Webhook-хендлер ничего не считает:** проверяет секрет, дедуплицирует, кладёт событие в
  очередь `jobs` в Postgres и сразу отвечает 200. LLM и сеть — только в фоновом воркере.
- **Подбор рекламы:**
  1. частотные правила до LLM: пост ≥ 80 символов, нет открытого предложения, ≥ 3 поста и
     ≥ 120 минут с прошлой рекламы, ≤ 3 реклам в сутки;
  2. анализ поста — 1 вызов LLM, строгий JSON, кэш по хэшу текста: тема, категория,
     brand safety (`unsafe` — рекламы не будет);
  3. поиск — эмбеддинг `summary + topics` → pgvector cosine top-20;
  4. фильтры — блоклист и регулируемые категории канала, бюджет, отказы за 14 дней,
     одно объявление не чаще раза в 7 дней;
  5. оценка без LLM: `0.6·sim(пост, объявление) + 0.25·sim(профиль канала, объявление) +
     0.15·выплата`, порог `MIN_MATCH_SCORE=0.35`;
  6. объяснение «почему» — 1 вызов LLM.
- **Калибровка похожести:** у `multilingual-e5-small` косинус даже несвязанных русских текстов
  ≈ 0.77, у точных попаданий 0.84–0.88. Поэтому косинус нормируется в `[0, 1]` по диапазону модели
  (`sim_floor=0.78`, `sim_ceil=0.88` в `backend/src/ctxads/embeddings/e5_local.py`).
- Все внешние сервисы (MAX, LLM, эмбеддинги) — за интерфейсами с fake-реализациями для тестов.

## 4. Команда запуска через Docker

Нужны Docker с Compose v2, токен бота MAX и ключ NVIDIA NIM (см. [раздел 5](#5-переменные-окружения)).

**Локально (long polling, без домена):**

```bash
cp .env.example .env                                   # впишите MAX_BOT_TOKEN и LLM_API_KEY
MODE=polling docker compose --profile app up -d --build
docker compose exec app uv run --no-sync python -m ctxads.seed   # демо-каталог, один раз
docker compose logs -f app                             # логи бота
```

Первая сборка скачивает базовые образы и зависимости (образ ~3,4 ГБ, в основном torch).
Первый `seed` скачивает модель эмбеддингов e5 (~120 МБ) в том `hf-cache`.

**На сервере (webhook, HTTPS через Caddy + Let's Encrypt):**

```bash
DOMAIN=bot.example.com docker compose --profile demo up -d --build
docker compose exec app uv run --no-sync python -m ctxads.seed
```

Для webhook в `.env` дополнительно: `WEBHOOK_PUBLIC_URL=https://bot.example.com/webhook/max`,
`WEBHOOK_SECRET`, `PUBLIC_BASE_URL=https://bot.example.com`, `MINIAPP_URL=https://bot.example.com/miniapp/`.
MAX принимает webhook только по HTTPS на 443 с сертификатом доверенного CA.

<details>
<summary>Без Docker (для разработки)</summary>

Нужны Python 3.12, [uv](https://docs.astral.sh/uv/), PostgreSQL 16+ с pgvector, Node.js 22+.

```bash
cp .env.example .env
npm ci && npm run build          # frontend → frontend/dist
cd backend
```

`.env` один — в корне: backend при запуске из `backend/` читает `../.env`.

## 5. Переменные окружения

Шаблон — [`.env.example`](.env.example) (`cp .env.example .env`). Комментарии в `.env` пишите на
отдельной строке: после пустого `КЛЮЧ=` комментарий прочитается как значение.

**Обязательные:**

| Переменная | Назначение |
|---|---|
| `MAX_BOT_TOKEN` | токен бота MAX; также проверка подписи запусков мини-приложения |
| `LLM_API_KEY` | ключ NVIDIA NIM (`nvapi-…`) с build.nvidia.com |
| `LLM_MODEL` | модель NIM; по умолчанию `nvidia/nemotron-3.5-lightning-30b-a3b` |

**Основные (есть значения по умолчанию):**

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DATABASE_URL` | `postgresql+asyncpg://ctx:ctx@localhost:5432/ctx` | БД; в Docker подменяется на контейнер `db` |
| `PUBLIC_BASE_URL` | `http://localhost:8000` | адрес трекера кликов `/r/{token}` в кнопке «Подробнее» |
| `MINIAPP_URL` | пусто | публичный HTTPS-адрес мини-приложения (кнопка в боте) |
| `CLICK_SALT` | `change-me` | соль для хэширования IP в кликах — замените |
| `MAX_API_BASE` | `https://platform-api2.max.ru` | адрес MAX Bot API |
| `LLM_PROVIDER` | `openai_compat` | `openai_compat` (NIM) \| `yandexgpt` \| `gigachat` \| `fake` |
| `LLM_BASE_URL` | `https://integrate.api.nvidia.com/v1` | адрес OpenAI-совместимого API |
| `LLM_RPM` | `30` | клиентский лимит запросов к LLM в минуту |
| `EMBEDDER` | `e5_local` | `e5_local` (локальная модель) \| `fake` |
| `PLATFORM_FEE` | `0.3` | доля платформы |
| `PROPOSAL_TTL_MIN` | `120` | сколько минут предложение ждёт решения |
| `MIN_MATCH_SCORE` | `0.35` | порог соответствия рекламы посту |

**Только для webhook:** `WEBHOOK_PUBLIC_URL`, `WEBHOOK_SECRET` — без них бот в режиме webhook
не стартует.

**Опционально, запасной LLM:** `LLM_FALLBACK_PROVIDER`, `LLM_FALLBACK_API_KEY`, `LLM_FOLDER_ID`.

**Переменные запуска Compose** (задаются в командной строке, не в `.env`):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `MODE` | `webhook` | `polling` для локального запуска |
| `DOMAIN` | `localhost` | домен для Caddy (профиль `demo`) |
| `DB_HOST_PORT` | `5432` | порт БД на хосте, если 5432 занят |

## 6. Используемые порты

| Порт | Сервис | Доступ |
|---|---|---|
| `8000` | app (FastAPI: бот, мини-приложение, API, трекер) | только `127.0.0.1` хоста |
| `5432` | db (PostgreSQL + pgvector) | только `127.0.0.1`; меняется через `DB_HOST_PORT` |
| `80`, `443` | caddy (HTTPS, профиль `demo`) | публично — нужны для webhook MAX и Let's Encrypt |

HTTP-эндпоинты приложения:

| Путь | Что |
|---|---|
| `GET /healthz` | проверка живости |
| `GET /miniapp/` | мини-приложение MAX (собранный frontend) |
| `/api/miniapp/*` | API мини-приложения (запросы с подписью запуска MAX) |
| `GET /showcase` | витрина рекламодателя, только чтение |
| `GET /r/{token}` | трекер клика → 302 на рекламодателя с `utm_*` и `click_id` |
| `GET /postback?click_id=&amount=&sig=` | конверсия CPA, `sig = HMAC-SHA256(secret, "click_id:amount")` |
| `POST /webhook/max` | события MAX (только режим webhook) |

Исходящие соединения: `platform-api2.max.ru:443`, `integrate.api.nvidia.com:443`,
`huggingface.co` (скачивание модели при первом запуске).

## 7. Зависимости

- **Для запуска:** Docker с Compose v2 (проверено на Docker 29.8, Compose 5.5).
- **Без Docker:** Python 3.12 + uv, PostgreSQL 16+ с pgvector, Node.js 22+ и npm.
- **Backend** ([`backend/pyproject.toml`](backend/pyproject.toml), [`uv.lock`](backend/uv.lock),
  [`requirements.txt`](requirements.txt)): FastAPI, uvicorn, httpx, Pydantic v2, SQLAlchemy 2
  (async) + asyncpg, Alembic, pgvector, openai (клиент NIM), sentence-transformers + torch (CPU).
- **Frontend** ([`package.json`](package.json), [`package-lock.json`](package-lock.json)):
  React 19, Vite 6, TypeScript, `@maxhub/max-ui`.
- **Внешние сервисы:** MAX Bot API, NVIDIA NIM, Hugging Face (модель `intfloat/multilingual-e5-small`).

## 8. Данные и интеграции

**Хранилище — PostgreSQL** (том `pgdata`): каналы и их настройки, посты с результатом анализа,
объявления и рекламодатели, предложения, размещения, клики, конверсии, проводки (ledger),
очередь задач. Схема — миграции `backend/alembic/versions/0001–0004`, применяются автоматически
при старте контейнера. Модель эмбеддингов кэшируется в томе `hf-cache`.

**Интеграции:**

| Сервис | Для чего | Что уходит |
|---|---|---|
| MAX Bot API | события канала и лички, отправка сообщений, публикация, права, просмотры | — |
| NVIDIA NIM (OpenAI-совместимый API) | анализ поста и объяснение подбора, 2 вызова на пост | только публичный текст поста и объявления |
| Hugging Face | однократное скачивание модели e5 | — |
| Рекламодатель (postback) | подтверждение конверсий CPA | — |

**Персональные данные:** храним только MAX ID, имя и факт согласия админов/рекламодателей.
Данные подписчиков канала не собираем; IP в кликах — только соль + хэш.

Сертификат MAX API выпущен УЦ Минцифры: корневой сертификат лежит в пакете
(`backend/src/ctxads/max_api/russian_trusted_root_ca.pem`) и используется только клиентом MAX.

## 9. Работа с тестовыми данными

- **Демо-каталог** — [`backend/seed/ads.yaml`](backend/seed/ads.yaml): 30 объявлений от
  10 вымышленных рекламодателей, по 3 в категориях Здоровье, Медицина, Спорт, Еда, Технологии,
  Образование, Финансы, Путешествия, Красота, Дети. ИНН и ERID — демонстрационные. Загрузка
  (повторный запуск безопасен — объявления обновятся, дублей не будет):

  ```bash
  docker compose exec app uv run --no-sync python -m ctxads.seed
  ```

- **Офлайн-демо всего сценария без токена MAX** — MAX заменён фейком, LLM — `FakeLLM`,
  эмбеддинги и pgvector настоящие. Создаёт отдельный демо-канал в той же БД:

  ```bash
  docker compose run --rm app uv run --no-sync python -m ctxads.demo
  ```

- **Автотесты** (в образ не входят, запускаются из исходников; в сеть не ходят, MAX и LLM
  замоканы, фикстуры событий — `backend/tests/fixtures/updates/*.json`):

  ```bash
  docker compose exec db createdb -U ctx ctx_test     # тестовая БД, один раз
  cd backend && uv sync && uv run pytest -q
  ```

- **Посты для ручной проверки** (длиннее 80 символов, на темы каталога):
  - *Спорт:* «Как выбрать кроссовки для бега, если вы только начинаете. Для пробежек по асфальту
    нужна амортизация, для трейла — протектор. Тренировки три раза в неделю — лучший старт.»
  - *Здоровье:* «Как бургер влияет на сахар в крови. После фастфуда уровень глюкозы резко растёт,
    а через час падает — отсюда усталость и снова голод.»
  - *Без рекламы (brand safety):* «Трагедия на трассе: в результате крупной аварии погибли пять
    человек, ещё десять пострадавших доставлены в больницы.»

## 10. Пошаговая проверка продукта

**Без ключей MAX и NIM** — весь сценарий в офлайн-демо (бот к MAX не подключается, поэтому
вместо запуска сервиса — одноразовый контейнер):

```bash
cp .env.example .env                  # ключи можно не заполнять
docker compose up -d db
docker compose run --rm app sh -c "uv run --no-sync alembic upgrade head && uv run --no-sync python -m ctxads.demo"
```

**С настоящим ботом:**

1. Запустить по [разделу 4](#4-команда-запуска-через-docker), загрузить каталог (`seed`).
2. `docker compose logs -f app` — дождаться строки `long polling started`.
3. В MAX написать боту `/start` → «✅ Принимаю».
4. Добавить бота администратором своего канала с правами «Читать все сообщения» и
   «Публиковать сообщения».
5. Опубликовать в канале пост про бег (текст — в [разделе 9](#9-работа-с-тестовыми-данными)).
6. В личке с ботом нажать «✅ Одобрить».
7. Через минуту проверить канал.
8. Опубликовать ещё 3 поста, затем пост про трагедию — рекламы быть не должно.
9. `/stats` — статистика канала; `/settings` — запретить категорию.
10. `/cabinet` — создать объявление на тему будущего поста, опубликовать такой пост.
11. Открыть `http://localhost:8000/showcase` — объявления, бюджеты, размещения.

## 11. Ожидаемый результат

| Шаг | Результат |
|---|---|
| офлайн-демо | в консоли: подключение канала → предложение «ЛабТест — анализ на глюкозу» к посту про бургер → блок категории → пост о трагедии без рекламы (`skip_reason=unsafe`) → предложение «Бегун — кроссовки» → публикация с `#Реклама` → клик → `/stats` с доходом |
| `/healthz` | `{"status": "ok"}` |
| логи при старте | `bot @<имя_бота> (id …), mode=polling` и `long polling started` |
| `/start` | условия и кнопка «Принимаю»; после нажатия — инструкция по подключению канала |
| бот добавлен в канал | в личку: «✅ Канал «…» подключён. Подписчиков: N. Профиль: …» |
| пост про бег | через 5–60 с в личку: предложение «Бегун — беговые кроссовки…», «почему», модель оплаты, ожидаемый доход, 4 кнопки |
| «Одобрить» | «✅ Одобрено, выйдет в ЧЧ:ММ», через минуту в канале — пост с `#Реклама. ООО «Бегун Спорт», ИНН …. erid: …` и кнопкой «Подробнее», в личку — «📣 Реклама опубликована» |
| пост о трагедии | предложения нет (пост помечен `unsafe`) |
| `/stats` | размещения, просмотры, клики и заработок за 7 и 30 дней |
| `/cabinet` | мастер из 7 шагов, превью, после «Запустить» объявление в меню со статусом 🟢 |
| `/showcase` | таблица объявлений с бюджетами и результатами |

Если к посту не пришло предложение, причина записывается в БД:

```bash
docker compose exec db psql -U ctx -d ctx -c "select left(text,50), skip_reason from posts order by id desc limit 5;"
```

`too_short` (короче 80 символов), `open_proposal`, `too_few_posts`, `too_soon`, `daily_limit`,
`unsafe`, `no_match`, `llm_unavailable`.

## 12. Известные ограничения

- **Платежей нет:** ledger считает списания и начисления, деньги никуда не уходят; пополнение
  бюджета в кабинете — демо.
- **Маркировка:** ERID демонстрационный, интеграции с ОРД нет. Рекламодатели из кабинета бота
  ИНН не указывают — маркировка `#Реклама. {название}. erid: …`. Рекламодатели и ИНН в seed —
  вымышленные.
- **Модерации объявлений нет:** объявления из кабинета сразу попадают в подбор.
- **Клики** считаются только при публичном HTTPS-адресе (`PUBLIC_BASE_URL`). С `localhost` MAX не
  принимает ссылку на трекер, поэтому кнопка ведёт сразу на рекламодателя, клики не считаются.
- **Мини-приложение** работает только при открытии из MAX: API принимает запросы с подписью
  запуска MAX, тестового обхода входа нет.
- **Одно предложение за раз:** пока в канале есть неразобранное предложение, новые посты
  пропускаются.
- **LLM:** бесплатный NVIDIA NIM ~1000 запросов и очередь; при долгой очереди пост пропускается
  с причиной `llm_unavailable`. Прогноз дохода в предложении — грубая оценка (охват 30%,
  CTR 1%, конверсия 5%).
- **Webhook и polling не работают одновременно:** пока у бота активна webhook-подписка, long polling
  не получает событий.
- **Два автотеста** (`test_polling_app_runs_worker_scheduler_and_poller`,
  `test_worker_runs_update_job_end_to_end`) падают после 25.09.2026: время в тестовых часах
  зафиксировано. На работу бота не влияет.
- **Не проверено по документации MAX** (`TODO(verify-api)`, код устойчив к отсутствию полей):
  поле `notification` в `POST /answers`, параметры `DELETE /messages`, формат `message_ids` в
  `GET /messages`, структура `Callback`, картинка в рекламном посте по `url`.

## 13. Остановка и повторный запуск

```bash
# остановить, сохранив данные и кэш модели
docker compose --profile app stop

# запустить снова (без пересборки; миграции применятся автоматически, seed не нужен)
MODE=polling docker compose --profile app up -d

# после изменения кода — с пересборкой
MODE=polling docker compose --profile app up -d --build

# удалить контейнеры (тома с БД и моделью остаются)
docker compose --profile app down

# полный сброс: удалить и данные БД, и кэш модели (потом снова нужен seed)
docker compose --profile app down -v
```

Для сервера — то же с `--profile demo` и `DOMAIN=…` вместо `MODE=polling`.
Проверка после перезапуска: `docker compose ps` (сервисы `running`, `db` — `healthy`) и
`docker compose logs -f app`.
